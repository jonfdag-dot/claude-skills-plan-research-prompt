# Scenario selection and instruction forms

Load this reference only after FOCUSED_EVAL or FULL_EVAL admission under the [canonical policy](../../skill-creator/references/verification-and-eval-admission.md). Routine skill changes remain STATIC. The methods here create no ordinary cases, baselines, repetitions, dispatch or scope expansion.

## Match scenarios to the admitted property

| Skill content | Candidate scenario | Observable result |
|---|---|---|
| Policy or required behavior | A realistic conflicting incentive inside an isolated authorized workload | Required behavior and task correctness, each checked separately |
| Technique | Representative application, variation or missing input | Correct application or an explicit supported failure |
| Pattern | Recognition, application and a counterexample | Selects the applicable pattern and respects its boundary |
| Reference | Lookup and application of relevant information | Finds the supported fact and uses it correctly |

A recitation question tests recall, while an action scenario tests behavior in the supplied environment. Neither proves general compliance. Use existing representative cases first; new cases require a named coverage gap within admission. There is no default minimum number of pressures or cases.

## Candidate instruction forms

Before rewriting, identify the actual observed failure. Different forms communicate different kinds of requirements:

| Observed problem | Candidate form | What to verify |
|---|---|---|
| Skips a required step | A scoped directive with its trigger and required action | The step occurs when required without blocking authorized exceptions |
| Produces the wrong output shape | A positive output contract or example | Required parts and relationships are present |
| Omits a field | An explicit field in the output structure | The field carries the required information |
| Applies behavior too broadly | A condition tied to an observable predicate | Intended positive and negative boundaries |
| Misreads an exception | Separate conditions with precedence stated | Both permitted and prohibited cases |

These are design options, not proven rankings of instruction styles. Preserve qualifications that matter to correctness or authority; a prohibition, recipe or template can still be misapplied.

## Historical wording observations

The earlier reference described a dispatch-prompt wording comparison as “fully separated distributions,” reported that a prohibition arm produced more unwanted content than a recipe arm, and reported that a nuance clause degraded consistency. Preserve these as historical reports and hypotheses; they do not establish current-model superiority or a universal ban on prohibitions or nuance.

Recover and inspect the original artifacts before relying on a numerical or causal conclusion. A fresh experiment still needs canonical admission. ## Address demonstrated failure without discarding work

Write the smallest change that answers the admitted failure. Do not add a counter for every hypothetical rationalization or force a skill to reject legitimate judgment.

```markdown
If required verification has not run, preserve the implementation, identify the requested behavior and run the smallest authorized check that establishes it. Report unavailable evidence and stop before an unauthorized action.
```

A failure table can document an observed mistake and the relevant requirement:

```markdown
| Observed mistake | Required response |
|---|---|
| Claimed success from an unrun command | Run the applicable check or report that completion is unverified |
| Treated a worker report as acceptance | Verify the decisive artifact against the assigned requirement |
| Deleted user edits to satisfy a teaching sequence | Preserve the edits and make the smallest authorized repair |
```

These examples preserve existing work. They replace the earlier destructive “delete code and start over” teaching examples; no scenario authorizes that action.

## Repair, evaluate and stop

Capture the trigger, affected requirement, observed artifact and actual check. A model's suggested rewrite is a hypothesis to inspect, not a reason to add it verbatim. Re-evaluate only evidence invalidated by an authorized repair, within the same remaining allowance. Do not expand a campaign because another rationalization is interesting.

Report equally passing baselines, failures and inconclusive samples. Stop at the admitted acceptance or budget boundary. Passing one scenario establishes that observation, not that the skill is “bulletproof.”
