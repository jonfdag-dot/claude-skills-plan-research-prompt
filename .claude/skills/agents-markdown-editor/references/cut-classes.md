# Cut classes

Judge each directive against its required outcome, authority, effective loading and concrete failure mechanism. A predicted model default is a review lead, never proof that a rule can be deleted. Use the qualified forty-pattern catalog and research standards below for semantic cleanup; classification alone never authorizes removal.

| Class | Pattern and decision | Action and preservation | Tier |
|---|---|---|---|
| class-1 | Code-derived inventory or repetitive directory tour | Propose DELETE/MOVE only for redundant detail; KEEP unique architecture seams, decisions and otherwise unavailable orientation. No overview-first ranking. | judgement |
| class-2 | Product narrative | KEEP facts that determine scope, behavior or user requirements; ASK to move explanatory detail with a pointer. Tool-call differences alone cannot judge value. | judgement |

## Tiers and effort

Tier 1 proves a defect from inspected text, resolved paths/consumers or deterministic results. Validate linter scope before adopting its verdict; a block may be a false positive or ownership safeguard. Tier 2 proposes a discretionary change and names its mechanism, counterevidence and preservation boundary. No rule requires a cut, a pitfall or a minimum saving per file.

A required outcome such as preventing cross-tenant reads differs from an effort mandate such as repeating a full suite. Preserve the outcome and its genuine acceptance checks; narrow only the unjustified extra work. An unmet exact-count contract proves noncompliance, never permission to repeal that contract.

## Qualified removal and narrowing principles

Select this reference for semantic cleanup of agent instruction Markdown, including imported or scoped instruction documents. These principles support future CLAUDE.md/AGENTS.md edits and can inform their authorized supporting references; they do not expand this skill into editing every Markdown file or changing product policy.

### Use and evidence

Review equivalent obligations and combinations after runtime precedence. Compare “stop after passing checks” with session-rerun, final-agent and research-quota clauses even when their vocabulary differs. Classify each candidate's current owner and exact trigger; propose the smallest correction with original/replacement text, evidence level, proposed effect and preserved invariant. No finding or cut is a valid outcome.

This catalog is an adopted instruction-review taxonomy, not a local performance experiment. Inspect the actual loaded instructions, source owners and acceptance evidence before applying a class. The source installation's audit reports and private evidence IDs are outside this export.

For each material research/model claim, name its source, model/version, workload and actual inspection date. Separate documented source content, vendor outcome claims, independent measurements, local observations and proposed mechanisms. Follow the original citation for an unsupported or newly refreshed claim; correct moving links and exact authorship. Repeated coverage of one study/publisher is one evidence lineage. A Karpathy-inspired repository is not proof of Karpathy authorship.

Keep consequential counterevidence visible: [Gloaguen et al., v3](https://arxiv.org/html/2602.11988v3), SWE-bench Lite/Python CTXbench with older GPT/Claude/Qwen models, does not establish a universal success penalty or overview-first deletion order; nonsignificant results establish neither equivalence nor harm. [Lulla et al., v2](https://arxiv.org/html/2601.20404v2), GPT-5.2-Codex on 124 paired small PR tasks, reports lower median runtime/output tokens alongside slightly higher median total tokens and limited correctness inspection. Distinguish means/medians, input/output/total tokens, per-task cost and cost per correct result. [Cursor's GPT-5-Codex harness account](https://cursor.com/blog/codex-model-harness), a first-party internal benchmark claim dated 2025-12-04, concerns API reasoning-state continuity, a separate mechanism from Markdown wording. Equal visible prompts do not control runtime loading, hidden instructions, tools, permissions, model effort or task state.

Byte reduction measures size only. A plausible expansion risk is not evidence that a rule caused a past loop; that requires relevant existing traces or an admitted comparison. Provider guidance is evidence, never authority to remove explicit requirements. No unsolicited traces, telemetry, model/effort/hook changes or behavioral campaign follow from this review; use the canonical verification admission policy for any empirical question.

### Forty patterns with preservation boundaries

| ID | Pattern to remove, narrow or move | Replacement principle and exception |
|---|---|---|
| R01 | Generic think harder, be extremely thorough, consider everything | State the required outcome or uncertainty. Keep reasoning effort under user control. |
| R02 | Mandatory step-by-step hidden reasoning output | Request a concise rationale or evidence when needed, not private deliberation. |
| R03 | Whole-repository reading or a full intent map before every edit | Read the owner, relevant callers/contracts and unresolved risks. A requested map remains a valid deliverable. |
| R04 | Every unfamiliar file requires a durable plan | Plan when sequencing, uncertainty or risk affects correctness; unfamiliarity first permits focused discovery. |
| R05 | Every task requires a plan file, approval cycle or handoff document | Use the current task record; preserve explicitly required approvals and durable plans for work that needs them. |
| R06 | Large repository size automatically selects the heaviest workflow | Choose depth from the affected behavior and consequence, not total lines of code. |
| R07 | Generic final verification after already passing applicable checks | Reuse the existing evidence; add a check only to close a named unresolved requirement. |
| R08 | Typecheck, lint, build and full suite on every task | Match checks to affected behavior; preserve genuine repository and release gates. |
| R09 | Rerun tests whenever a session resumes | Session age alone does not invalidate evidence; assess relevant code, inputs and environment changes. |
| R10 | A file hash change invalidates every prior result | Determine which criterion the change affects; retain evidence for unchanged criteria. |
| R11 | An independent verifier is mandatory for every patch | Keep independence where requested, consequential, or an established acceptance requirement. |
| R12 | Reviewers must find a pitfall or improve something | Findings require a correctness or requirement gap; no findings is valid. |
| R13 | Repeat until completely certain or nothing can improve | Stop when requested behavior and applicable checks pass; report remaining optional work separately. |
| R14 | Repeat an unchanged failing command | Change a relevant condition or ask a new diagnostic question; otherwise report the precise blocker. |
| R15 | Fix every failure encountered before proceeding | Distinguish requested/affected failures from unrelated pre-existing defects; preserve truthful status. |
| R16 | Create permanent tests, fixtures or proof reports solely to show work | Retain tests that protect requested behavior; scratch verification may stay temporary. |
| R17 | Every task needs workers, a final stitch agent or a minimum agent count | Delegate bounded independent work when isolation, expertise or parallelism helps; keep integration ownership. |
| R18 | Every read-heavy operation should be delegated | Compare dispatch/coordination cost with the actual independent task; reuse returned evidence. |
| R19 | A completed text report automatically triggers another worker turn | Continue only for named open items; finish started work and preserve finite continuation bounds. |
| R20 | Any uncertainty requires stopping and asking | Resolve routine reversible choices from conventions; ask about material scope, risk, authority or external effects. |
| R21 | Production-ready, future-proof or comprehensive as unlimited scope | Name current acceptance; do not infer speculative features, fallback layers or infrastructure. |
| R22 | Adding to a large file requires unrelated cleanup | Extract only where needed for the requested change; do not manufacture adjacent scope. |
| R23 | Every task requires deep research, multiple searches or all registers | Retrieve relevant prior evidence and investigate remaining gaps; retain required source independence without quotas. |
| R24 | All non-authority blockers are always solvable through more research | Distinguish access, consent, contracts and unavailable evidence; further search cannot manufacture authority. |
| R25 | Fill documents to a cap or reject them below a length floor | Treat caps as ceilings; judge coverage against required decisions, contracts and evidence. |
| R26 | Always load one or several skills, including trivial replies | Select a skill because its capability is needed; preserve explicit user invocation. |
| R27 | Broad topic triggers, such as all database work activates migration procedures | Name the actual operation that requires the workflow. |
| R28 | Mandatory graph-first or tool-first discovery for every question | Choose the surface that resolves the question; preserve impact analysis for relevant dependency changes. |
| R29 | Automatically repair a conflicting skill during another task | Follow the owning contract, report the conflict and repair only within authorized scope. |
| R30 | Directory tours, dependency catalogs and copied code descriptions in root files | Retain non-obvious facts and entry pointers; move derivable inventory to its existing owner. |
| R31 | Long conditional procedures in always-loaded rules | Keep a short trigger/pointer and load the procedure when relevant; an import does not save context. |
| R32 | The same general policy repeated in global, project and nested files | Give it one owner per effective runtime chain; retain necessary standalone cross-runtime mirrors. |
| R33 | Historical copies and templates named as live instruction files | Preserve their content under non-discovered names after checking consumers and ownership. |
| R34 | Hardcoded counts, model names, deadlines or commands without an owner | Link the authoritative current value; resolve actual contradictions from accepted decisions. |
| R35 | A Markdown prohibition described as technical enforcement | Distinguish a binding instruction from a hook/permission/CI mechanism and its actual coverage. |
| R36 | Mandatory before/after model trials for every instruction edit | Use static verification by default; admit finite behavioral trials only for an unresolved empirical question. |
| R37 | Deleting all MUST/NEVER or all untested preferences | Preserve explicit requirements and preferences; emphasis and lack of an incident are not defects by themselves. |
| R38 | Optimizing bytes by deleting product safeguards | Keep privacy, isolation, consent, billing, migrations, release approvals and domain invariants regardless of model age. |
| R39 | Assuming low skill/tool usage means it should be removed | Inspect ownership and task relevance; do not introduce unsolicited usage instrumentation or retirement loops. |
| R40 | Changing prompts, model, effort and hooks together | Separate interventions if a later behavioral comparison is authorized; this report requires none. |


### Operator-directed process removal

When the operator explicitly requests removing generic thinking, planning or post-coding verification instructions, propose DELETE for those obligations rather than automatically narrowing them into another mandatory workflow. Model-default claims explain the operator's preference; they do not prove correctness, authorize application or repeal protected product requirements. Without that removal request, retain the ordinary KEEP/REWRITE/DELETE judgment and approval contract.

| Encountered pattern | Disposition in the requested removal pass | Preservation boundary |
|---|---|---|
| `Think. Simplify. Surgical. Verify.`, type-design tutorials, signature-first recipes, forced debugging hypotheses or evidence labels for every claim | Delete generic process/narration scaffolding; retain only explicitly selected code conventions | Scope, truthfulness, no hidden type errors and no silent failures remain |
| Unfamiliarity or any edge-function edit reinstates a plan, a complete digest preread or a six-stage workflow | Delete the compulsory trigger/stages; retain conditional reference and plan-storage pointers | Approved decisions, known regressions and migration consent remain |
| Observable-check declarations, verification before saying done, blanket test commands, final Stitch/verifier agents | Delete generic obligations and their duplicate clauses | Genuine release/security gates, money/data controls, requested reviews and useful test locations remain |
| Stop-after-checks rules and detailed justifications for additional checks survive after the generic verification mandate is deleted | Propose deleting orphaned counter-rules instead of retaining the same process in reverse | Specific evidence-reuse or finite-retry requirements stay when independently required |
| Three mandatory similarity searches plus negative evidence before proposing creation; adding to a large file forces unrelated cleanup | Remove the search/proposal ritual and compulsory adjacent changes | Explicit scope-expansion approval and suitable existing code remain |

Search the effective loaded chain and source emitters for equivalent obligations after selecting cuts. A root edit is incomplete when an unscoped rule, native copy or generator restores the removed mandate. Inspect the consumed property: literal section headings, transformation anchors, parsed vocabulary and protected native sections have different contracts. Propose supporting changes explicitly; do not silently broaden approval or patch only generated output. In a temporary copy, exercise the actual writer when needed to establish that it accepts the changed anchors and preserves the intended native result. This is a deterministic contract check, not a model evaluation or permission to run product commands.

Use [worked examples 14–16](worked-examples.md#14-explicit-removal-without-a-replacement-workflow) for the concrete encounters and tool-failure boundary. Neither this catalog nor a keyword hit establishes local performance harm or automatic deletion authority.

### Practical sequence

Resolve confirmed contradictions and placement hazards first, then narrow unconditional process expansion, then consolidate actual loaded overlap and move conditional detail. Recover accepted authority for conflicting dates, grades or releases; do not choose the cheaper value. Inspect generators, vocabulary parsers and line-count consumers before modifying their input. An observed mismatch does not repeal the contract.

Preserve non-obvious commands, architecture seams and decisions, required checks and permissions, truthful status, privacy/consent, isolation, billing/refunds, data integrity, migration/release/paid-operation approvals and external obligations. Keep explicit deep research and source independence when required; distinguish them from arbitrary search quotas. No incident history is needed to retain a proactive safeguard.

For moves, name the existing owner and reliable trigger and calculate the effective loaded delta. Do not create adjacent architecture, instrumentation, hook changes or tracking machinery to demonstrate cleanup. A historical template can be preserved under a non-discovered name after consumer inspection; preserving its content does not require retaining a hazardous ancestor instruction filename.
