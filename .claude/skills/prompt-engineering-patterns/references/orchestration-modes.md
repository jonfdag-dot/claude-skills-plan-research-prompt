# Wording Workflow and Escalation Requests

Use this reference to write a requested workflow clause after its execution design is chosen. SDD owns inline versus delegated execution, dependencies, team size, native role selection, scheduling, stopping, and recovery. This reference does not choose a topology or change a session setting.

## Carry the chosen design

Name the required outcome and carry phases, dependencies, ownership/effect boundaries, evidence and stopping conditions that the chosen contract actually uses. Describe parallel work only when SDD has established that it is independent and dispatchable. Do not add a worker per item, universal verifier, scout phase, or sample campaign merely because the prompt can request it.

A workflow request cannot manufacture missing tools, approved spending, native isolation, model policy, or deployment authority. When the prompt depends on a runtime-specific workflow feature, identify the actual runtime/version and exposed contract; do not paste an unrelated runtime's keyword or concurrency ceiling.

## Word escalation precisely

Use an observable unresolved condition and the next permitted action rather than “use more effort” or “keep trying until it works.” The trigger, response, and limit come from the accepted task and host policy.

```text
If the named acceptance check fails, preserve its input, artifact version, actual result, and remaining requirement. Repair only within the assigned authority and applicable correction limit. If the limit is reached or a required decision/input is missing, return the evidence and recoverable partial state to the root.
```

This clause words a supplied rule; it does not authorize a new repair cycle. A clarification or context continuation is not a failed correction. Changing workers or sessions does not reset defect history or an explicit whole-run allowance.

When a requested stage needs a reserved user decision or operation approval, retain that boundary and specify the concrete handoff. If the selected runtime cannot pause there, the execution owner must choose a supported staged design; prompt wording cannot bypass the boundary.

## Distinguish bounds and outcomes

Use SDD's [bounds and completion](../../subagent-driven-development/references/evidence-handoff.md#bounds-and-completion). A per-turn timeout, session setting, workflow size hint, retry delay, or agent concurrency limit is not the whole-task stopping condition. Define completion from the integrated outcome and required checks. At a real limit, preserve remaining work rather than silently narrowing the outcome.

If a cap limits review/research coverage, require the actual examined scope and unexamined remainder. An inaccessible source or failed tool is unverified evidence, not a negative finding.

## Preserve native policy

Effort/model values and permissions belong to the selected native configuration and relevant provider integration guidance. Do not alter the user's root settings, substitute persona text for a native specialist, or instruct a worker to override its model pin while composing the request.

Vendor workflow mechanics, published scale limits, caching behavior, and historical token comparisons are cataloged in [sources-and-contradictions.md](sources-and-contradictions.md). Inspect the applicable version when needed; those observations do not establish the local task's ideal roster, cost, or benefit. Report unavailable accounting as unavailable, without inventing an efficiency claim.
